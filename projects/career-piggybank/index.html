서비스 개요

문제 정의

긱워커는 경력 기록이 흩어져 있고, 수입이 들어오는 시기와 소득 공백이 일정하지 않습니다. 은퇴 시점도 정해져 있지 않아 월급에 맞춘 예산으로는 다음 입금까지 얼마나 남겨야 할지 판단하기 어렵습니다. 이력 관리, 입금 시 예산 배분, 은퇴 준비에 같은 사용자 정보를 쓰는 데모를 만들었습니다.

구현 방향

거래는 규칙으로 먼저 분류하고, 판단하기 어려운 거래는 로컬 모델의 도움을 받습니다. 확정된 거래로 지표 14개를 계산하고 소득 구조와 근거 검사를 통과한 성향을 공통 프로필에 담습니다. 이 프로필을 예산과 목표, 수입 예측, 금융 코칭과 상품 후보에 활용합니다. 배분 금액은 코드로 계산하고, 사용자가 제안을 승인하거나 조정하면 SQLite 원장을 갱신합니다.

내가 맡은 일

4인 팀의 개발 담당으로 Expo 앱, FastAPI 백엔드와 Ollama 로컬 모델을 연결했습니다. 거래 분류, 공통 프로필, 제안 근거 표시와 승인 후 원장 갱신을 구현했습니다.

Python, FastAPI, Expo, TypeScript, Ollama, EXAONE 2.4B, EXAONE 7.8B, SQLite

전체 아키텍처

거래 이력에서 공통 프로필까지

  1. 확정 이력확정 원장과 사용자가 배분을 조정한 행동 기록을 입력합니다.
  2. FactSheet측정 항목 14개에 값, 정의, 표본 수와 근거 ID를 저장합니다.
  3. 통계와 모델 판독규칙과 통계로 수입 안정성, 소득원 구조를 계산합니다. EXAONE 7.8B는 근거 ID를 인용해 성향 4가지를 판독하고 코드는 근거와 방향을 검사합니다.
  4. 공통 UserProfile측정값과 검증을 통과한 성향을 한곳에 담습니다.

프로필을 쓰는 기능

  1. 예산과 목표 봉투세금, 경비, 생활비, 여윳돈의 배분을 제안합니다.
  2. 수입과 은퇴 준비입금 이력과 가정을 바탕으로 수입과 은퇴 준비를 계산합니다.
  3. 금융 코치와 상품 후보공통 프로필을 활용해 제안을 구성합니다.

예산 제안에서 원장 갱신까지

  1. 금액 계산배분 금액과 세금은 코드로 계산합니다.
  2. 근거 확인사용자가 앱에서 제안 금액과 근거를 확인합니다.
  3. 승인 또는 조정사용자가 배분안을 승인하거나 금액을 조정합니다.
  4. 갱신확정한 결정을 SQLite 내부 원장과 이벤트 기록에 반영합니다.

성향 판독의 근거와 점수를 대조해 모순된 판단을 보류

내가 맡은 일 EXAONE 7.8B 성향 판독, 근거와 방향 검사, 교정 재시도, 배분 화면의 근거 표시를 구현했습니다.

관찰과 원인

소득 공백에 대비해 여윳돈을 얼마나 남길지 제안할 때 위험을 감내하는 정도를 초기 기준으로 쓰고 있었습니다. 그런데 모델이 거래 기록에서 인용한 근거와 반대 방향으로 성향 점수를 내기도 했습니다. 허용 범위에 있는 0.9도 근거와 대조해야 오류를 발견할 수 있었습니다.

구현과 선택 이유

모델이 인용한 ID가 실제 측정 항목에 있는지, 근거의 방향과 최종 점수가 일치하는지 코드로 검사했습니다. 오류 이유를 모델에 전달해 한 번 교정하고, 다시 검사에 실패하면 판단을 보류했습니다. 검사를 통과한 위험감내 판독을 여윳돈 목표에 활용했고, 사용자가 여윳돈을 직접 조정한 이력처럼 실제로 인용한 근거를 앱에 표시했습니다.

  1. 테스트 입력과 응답모델이 F06을 근거로 인용하고 자기통제가 높다는 뜻의 0.9를 응답했습니다.
  2. 방향 불일치 검사F06은 자기통제를 낮추는 근거이므로 코드가 점수와 근거의 모순을 표시합니다.
  3. 교정 1회위반 내용을 전달한 뒤 새 응답을 코드로 다시 검사합니다.
  4. 재실패 시 보류판단을 중립값 0.5로 기록하고 근거 목록을 비웁니다.

검증 결과

성향 판독 검증확인한 결과
교정 재시도 도입정확도 63.6%에서 68.2%로 상승, 교정 후에도 방향 오류 0건
회수한 정답허용 목록 밖의 0.65를 0.7로 교정해 정답 한 건을 회수
규칙 대조군같은 평가에서 90.9%로, 재시도를 적용한 모델의 68.2%보다 높음
후속 검증 강화방향 검사 조건을 추가한 뒤 정확도 63.6%, 방향 오류 0건, 판단 보류 8건

평가 범위 합성 페르소나 13명의 성향 라벨 22개를 평가했습니다. 방향 오류는 높음과 낮음을 서로 반대로 단정한 경우입니다. 68.2%는 재시도를 처음 적용한 실험의 결과이고, 63.6%는 검사를 강화한 후속 구성의 정확도입니다.

입금 분류부터 원장 갱신까지 사용자 확인 절차 구현

내가 맡은 일 거래 분류와 검증, 제안 금액 계산과 사용자 승인 후 원장 갱신을 구현했습니다.

관찰과 원인

입금 내역에는 일감 매출과 환급, 개인 간 거래가 섞여 있습니다. 모든 입금을 같은 소득으로 처리하면 소득 통계와 예산 제안도 달라집니다. 분류와 원장 반영을 사용자가 확인할 지점을 마련했습니다.

구현과 선택 이유

정산과 환급을 식별하는 규칙을 먼저 적용하고, 판단이 어려운 거래는 EXAONE 2.4B가 세 관점에서 분류한 결과를 코드가 집계했습니다. 세금과 배분 금액은 코드로 계산하고, 코치가 말한 금액이 계산값과 다르면 근거가 적힌 템플릿으로 바꿨습니다. 사용자가 승인하거나 금액을 조정하면 원장과 이벤트에 기록하고 다음 제안에 반영했습니다.

검증 결과

자체 거래 분류 평가확인한 결과

자동 분류 결과골든셋 50건 중 44건, 자동 분류 44건에서 오답 0건
사용자 확인나머지 6건은 자동으로 확정하지 않고 사용자에게 확인 요청

평가 범위 거래 분류 골든셋은 성향 판독 평가와 별개입니다. 원장 기반 입금 제안은 저장된 공통 프로필을 사용하고, 별도 stateless 제안 API는 요청받은 프로필을 사용합니다. 데모에 표시하는 잔액 변화는 SQLite 내부 원장에서 이루어집니다.
