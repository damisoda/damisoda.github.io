문제 해결

검수·수정 루프의 직렬 측정과 중복 검증을 줄여 실행 시간 143.8초 → 98.8초

문제 원인

  • 시안 비교와 버튼 검사를 화면 크기별로 하나씩 순서대로 실행했습니다.
  • 같은 수정 실행 안에서 코드와 조건이 같은 정적 사본을 최종 묶음 검증에서 다시 검사했습니다.
  • 단계별 소요 시간 기록이 없어 병목이 어디인지 알 수 없었습니다.

해결 과정

  • 단계별 계측: 모델 사전 확인, 기준 화면 검증, 모델 호출, 후보 빌드·측정 시간과 Ollama 로드·생성 시간을 따로 기록했습니다.
  • 병렬화: 브라우저와 정적 서버는 공유하고 독립 컨텍스트에서 최대 3개를 병렬로 검사한 뒤, 결과는 입력 순서대로 모았습니다.
  • 검증 결과 재사용: 코드와 조건이 같고 이미 통과한 결과만 최종 검증에 재사용했습니다. 회귀·누락·흐름 실패가 있으면 재사용하지 않습니다.
  • 테스트: 입력 해시가 같은 통제 사례로 개선 전후 각 3회 실행했고, 자동 테스트 162개가 통과했습니다.

결과

  • 전체 실행 시간 중앙값 143.8초 → 98.8초 (−31.3%). 검사 51.7초 → 38.9초, 수정·재검증 92.5초 → 60.7초.
  • 여섯 실행 모두 같은 결함 2건을 해결했고 새 결함은 0건, 최종 CSS 해시도 동일했습니다.
  • 한계: 한 통제 사례의 결과이고 실행 순서를 무작위로 섞지 않았습니다. 모델 호출 횟수가 줄어든 것은 아닙니다.

어떤 문제를 다뤘나요?

AI가 만든 화면에도 글자 넘침과 버튼 가림이 남습니다. 수정이 맞는지, 다른 화면 크기에서도 동작하는지 확인할 근거가 필요했습니다.

어떤 일에 참여했나요?

Dify를 반드시 거치는 실행 흐름, Figma 자동 연결, 실제 검사 로그와 수정 전후 화면 등 요구사항을 구체화했습니다. AI 코딩 도구와 함께 구현을 수정하고, 코드 수정부터 재검증까지의 동작을 확인했습니다.

시스템은 어떻게 구성되나요?

  1. 입력
    • Figma 시안
    • 구현 코드(로컬 저장소)
  2. 실행 제어
    • Dify 워크플로 — 검사·수정 진입점
  3. 측정 (코드)
    • 실제 Chromium 브라우저
    • 요소 좌표·스타일·클릭 결과
    • 모바일 화면 크기 5개
  4. 판단·근거
    • Dify RAG: 관측한 CSS 경계·버튼 정보 → 판정 규칙·수정 사례 검색
    • 근거가 있는 추가 검사만 브라우저에서 실행
  5. 수정
    • Gemma 4 E4B (Ollama, 맥미니): 결함 보고·후보 파일 위치 → 파일 읽기 → 코드 편집
  6. 검증 (코드·사람)
    • 사본 빌드 · 전체 회귀검증
    • 실패 시 예산 안에서 재수정
    • 전후 비교 · 사람 승인

수정 성공 여부는 모델의 설명이 아니라 재측정과 테스트 결과로 판정합니다.

서비스는 어떻게 동작하나요?

  1. Figma 기준 연결
  2. 브라우저 측정
  3. 모델 코드 수정
  4. 회귀검증·사람 승인

판정에는 측정값을

요소 좌표·스타일·클릭 결과를 수집하고, 모델의 설명과 실제 검사 결과를 구분했습니다.

수정에는 검증을

파일 읽기와 코드 편집 뒤 사본을 빌드하고, 등록된 화면 크기와 사용자 흐름을 다시 검사했습니다.

속도 개선에도 같은 조건을

브라우저 검사를 병렬화하고 동일 정적 사본의 중복 검증을 줄이면서 검사 범위를 유지했습니다.
