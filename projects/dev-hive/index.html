서비스 개요

문제 정의

GitHub와 커뮤니티에는 AI 활용 사례가 빠르게 쌓입니다. Codex 자동화 글을 북마크해도 처음 쓰는 사람은 글 속 설정을 바로 따라 해도 되는지, 기본 사용법을 먼저 익혀야 하는지 판단하기 어렵습니다. 글을 읽은 뒤 다음에 볼 자료도 다시 찾아야 합니다. Dev-Hive는 흩어진 자료를 학습자가 지금 볼 수 있는 순서로 묶는 데서 출발했습니다.

구현 방향

여섯 소스에서 수집한 자료와 사용자가 올린 글에 LLM으로 주제와 난이도를 붙였습니다. 기존 주제와 가까운 글을 먼저 편입하고 남은 글을 묶어 새 주제를 만들었습니다. 추천 코드는 주제 간 선행관계, 학습자의 관심과 숙련도, 자료 난이도를 반영해 순위를 매깁니다. 읽은 뒤 남긴 피드백은 다음 추천에 쓰는 학습 상태를 갱신합니다.

내가 맡은 일

수집부터 지식그래프 구성과 추천까지 전체 흐름을 설계했습니다. 2패스 편입과 노드별 동적 임계값을 설계하고 구현했고, 하위 주제의 선행관계를 추천에 연결했습니다. 서비스 통합과 PR 리뷰도 맡았습니다.

Python, FastAPI, PostgreSQL, pgvector, EXAONE, GraphRAG, Next.js

전체 아키텍처

자료가 추천 후보가 되기까지

  1. 자료 수집여섯 소스와 사용자 업로드
  2. 품질 검사와 태깅LLM으로 주제와 난이도 추출
  3. 임베딩과 Auto-HKG기존 주제에 편입하고 잔여 글은 군집화
  4. 주제와 선행관계 저장PostgreSQL, pgvector
  5. 추천 후보 검색그래프 경로와 벡터로 검색

추천 순위와 학습 상태 갱신

  1. 학습자 상태 읽기관심사, 숙련도, 읽은 이력
  2. 추천 순위 계산난이도, 관련성, 선행 충족도, 다양성
  3. 추천 이유 제공LLM으로 1순위 이유 작성, 실패 시 템플릿 사용
  4. 피드백으로 상태 갱신이해, 어려움, 더 보기, 관심 없음을 규칙으로 반영

기존 주제부터 편입해 자동 생성 주제를 825개에서 24개로 줄였습니다

내가 맡은 일 Auto-HKG 설계, 주제 파편화 진단, 2패스 구조 구현과 DB 재구축

관찰과 원인

당시 편입 임계값 0.85는 관찰한 최대 유사도 0.816보다 높았습니다. 콘텐츠가 기존 주제에 들어가기 어려워 자동 생성 주제 825개 중 778개가 글 한 건짜리였습니다. 새로 생긴 주제도 다음 글의 편입 후보가 되어, 어떤 글부터 들어오느냐에 따라 기준이 달라졌습니다.

구현과 선택 이유

첫 단계의 후보를 기존 비자동 주제로 고정했습니다. 코사인 유사도 0.70 이상이면 해당 주제에 편입하고, 남은 글은 서로의 유사도가 0.65 이상인 연결을 따라 묶었습니다. 글이 3건 이상인 군집만 새 주제로 만들고 작은 군집은 가까운 주제에 편입했습니다. LLM에는 군집의 이름과 설명을 붙이는 일만 맡겼습니다.

  1. 1패스, 기존 주제 편입비자동 주제, 코사인 유사도 0.70 이상
  2. 2패스, 남은 글 군집화유사도 0.65 이상인 연결, 군집 크기 3건 이상
  3. 주제 이름 생성LLM에 군집 이름과 설명만 요청

평가 범위 콘텐츠 924건으로 DB를 재구축했습니다. 먼저 트랜잭션을 롤백하는 방식으로 검증한 뒤 적용했습니다. 연결요소 방식에서 최대 110건의 큰 군집이 남아 후속 분할 대상으로 기록했습니다. 다음의 902건 시간순 유입 실험은 데이터와 비교 조건이 다릅니다.

콘텐츠 분포가 바뀌면 주제마다 편입 기준을 다시 계산했습니다

내가 맡은 일 시간순 유입 비교, 노드별 임계값 설계와 구현, 선택적 적용과 고정 기준 대체 경로 연결

관찰과 원인

2패스로 주제 파편화는 줄었지만, 고정 임계값은 기존 콘텐츠의 유사도 분포에 맞춰져 있었습니다. 새 소스가 들어오자 각 글과 가장 가까운 주제 사이의 유사도 중앙값이 0.72대에서 0.63~0.65로 내려갔습니다. 기존 기준을 통과하지 못해 두 번째 단계로 넘어가는 글도 늘었습니다.

구현과 선택 이유

다른 주제의 글도 특정 주제와 높은 유사도를 보이는데, 그 정도가 주제마다 달랐습니다. 각 주제의 중심과 다른 주제 글 사이의 유사도를 모아 95번째 백분위수를 편입 기준으로 삼았습니다. 유사도 0.62 미만 구간의 편입 정밀도가 당시 진단에서 80%를 밑돌아 하한을 0.62로 뒀습니다. 그래프를 확장할 때 분포를 다시 읽고, 비교 표본이 없으면 고정 기준을 씁니다.

  1. 다른 주제 글과 비교각 주제 중심과 다른 주제 콘텐츠 사이에서 코사인 유사도 계산
  2. 95번째 백분위수 계산다른 주제에 속한 글의 유사도 분포를 사용
  3. 하한 적용노드별 임계값 = max(95번째 백분위수, 0.62)
  4. 1패스 편입가장 가까운 주제의 임계값을 새 글에 적용

추천 후보 400개 중 292개에 선행관계 점수를 반영했습니다

내가 맡은 일 하위 주제 분할, 선행관계 점수 계산 수정, 추천 근거 설명 연결

관찰과 원인

하나의 대주제에 여러 성격의 글이 몰려 있어 spherical k-means로 하위 주제를 나눴습니다. 이후 글은 하위 주제 ID를 가리켰고, 기존 선행관계는 부모 주제 ID에 남아 있었습니다. 추천 코드가 하위 주제 ID로만 조회하자 기존 관계를 놓쳤고, 해당 자료의 선행 점수가 중립값 0.5로 처리됐습니다.

구현과 선택 이유

하위 주제에 직접 정의된 관계를 먼저 찾고, 없으면 부모 주제를 한 번 더 조회했습니다. 찾은 선행 주제마다 사용자의 숙련도를 관계 가중치로 평균 내고, 이 점수를 난이도, 관련성, 다양성과 함께 추천 순위에 반영했습니다. LLM은 1위 자료의 이유만 설명하고, 설명이 실패하면 순위에 쓴 근거를 템플릿으로 보여줍니다.

  1. 선행관계 조회하위 주제 ID 우선, 관계가 없으면 부모 주제 조회
  2. 선행 충족도 계산선행 주제 숙련도의 관계 가중평균, 관계가 없으면 0.5
  3. 추천 점수 계산난이도, 관련성, 선행 충족도, 다양성으로 재정렬
  4. 추천 이유 제공1순위 이유를 생성하고 실패하면 템플릿으로 표시

선행 충족도 계산식

선행 주제마다 관계 가중치와 사용자의 숙련도를 곱해 더한 뒤, 전체 관계 가중치의 합으로 나눴습니다.

평가 범위 로컬에서 주제 그래프를 재구축한 뒤 선행관계가 추천 점수에 반영되는지 확인했습니다. 숙련도는 읽은 이력과 피드백으로 추정했습니다. 검증 범위는 추천 점수 계산과 학습자 상태 갱신입니다.
