GitHub 저장소인공지능 루키대회 1차 결선 진출
문제 해결운영하며 고친 것AI 판단의 한계다룬 문제참여한 일시스템 구조구현 선택검증과 한계

문제 해결

개인화 30%·문헌통계 70% 결합과 면적 상한 알림으로 정답 위치 포함률 52.78% → 63.00%

문제 원인

  • 본선 정책은 평균 6.19㎢에 알림을 보내고도 정답 위치 포함률이 52.78%였습니다. 평소 습관대로 이동한 경우에도 74.15%만 포함했습니다.
  • 행정경계 기준으로 넓게 보내면 포함률은 76.85%까지 오르지만, 면적이 59.05㎢라 면적당 효율은 1.30에 그칩니다.
  • 개인화 비중만 높이면(50·70·90%, res8) 예상과 반대 방향으로 이동한 경우의 포함률이 12.82~16.99%로 떨어졌습니다.

해결 과정

  • 두 지도의 독립 계산: 보호자 정보·행동 규칙으로 만든 개인화 보행 지도와 문헌 이동거리 분포로 만든 통계 지도를 따로 계산해 30:70으로 결합했습니다.
  • 면적 상한: 실제 발송 해상도인 H3 res9 구역의 합집합 면적을 5.8㎢로 제한하고, 그 안에서 확률이 높은 구역부터 골랐습니다.
  • 미채택 후보: 반대 방향 5% 추가안, 개인화 50/70/90%(res8), 방향 20% 예약안은 효율 개선의 95% 신뢰구간에 0이 포함되거나 준수 포함률이 떨어져 채택하지 않았습니다.
  • 테스트: 후보 선택용 경로와 분리된 새 확인 경로로 다시 평가했습니다. 합성 인물 39명, 경로 351개, 1·2·4·6시간 시점, 설정별 2,808판정이며, 신뢰구간은 39명 군집 부트스트랩 10,000회로 계산했습니다.

결과

  • 전체 포함률 52.78% → 63.00% (+10.22%p), 평소대로 이동한 경우 74.15% → 96.69%.
  • 평균 알림 면적 6.19㎢ → 5.77㎢, 면적당 효율 8.52 → 10.92 (+28.18%).
  • 한계: 반대 방향 이동의 포함률은 30.45% → 27.56%로 2.88%p 낮아졌습니다. 합성 시뮬레이션 결과이며 실제 발견률은 검증하지 않았습니다.

운영하며 고친 것

배포한 서비스를 직접 운영하며 사용자가 겪은 문제를 고친 기록입니다.

  1. 2026.10.26

    시민 제보가 '전송 중…'에서 멈추고 저장되지 않음

    원인
    제보 접수가 같은 사건의 재예측(외부 도로망 로딩 최대 63초)을 기다리는 잠금 안에서 처리됐고, 예측 작업과 같은 계산 큐 뒤에 줄을 섰습니다.
    조치
    접수증을 먼저 저장하고 바로 응답하도록 바꿨습니다. 구조화·재예측은 백그라운드 작업자 2개가 처리합니다. 같은 submission_id의 재전송은 한 건으로 셉니다. 30초가 지나면 다시 확인하는 방법을 안내합니다.
    결과
    제보 저장이 분석·재예측 성공 여부와 분리됐습니다. 서버가 재시작돼도 대기 중인 분석을 이어서 처리합니다.
    PR 보기
  2. 2026.10.26

    고정 지도 밖 지역(망원) 시연에서 예측이 동작하지 않음

    원인
    KINTEX 고정 지도 범위 밖의 신고는 지역 도로망 로딩을 건너뛰는 분기가 있었습니다.
    조치
    준비된 지역의 도로망을 비공개 Supabase Storage에 저장했습니다. 요청 반경 확인과 SHA-256 검증을 거친 뒤 서버 캐시에서 재사용합니다.
    결과
    망원역 반경 6.5km 도로망(노드 54,068개)을 처음 불러올 때 19.565초, 재사용할 때 0.288초가 걸렸습니다. 외부 지도 요청 없이 예측합니다.
    PR 보기
  3. 2026.10.30

    결선 부스에서 같은 체험을 반복해야 함

    원인
    체험할 때마다 보호자 온보딩 대화를 처음부터 다시 진행해야 했습니다.
    조치
    확인 대기 중인 온보딩 대화를 템플릿으로 저장하고, '다음 체험 준비'로 이전 자료를 정리하게 했습니다. 이 기능은 부스 전용 계정에서만 쓸 수 있습니다.
    결과
    배포 후 61초 동안 성공 RPC 120건, 실패·재시작 0건을 확인했습니다. 일반 계정에는 진행자 영역이 보이지 않습니다.
    PR 보기
  4. 2026.11.04

    배포 앱에서 동선 예측이 지연됨

    원인
    부가 기능인 주변 산책 장소 조회가 외부 지도 미러의 시간초과를 기다리며, 예측과 같이 쓰는 큐를 31~35초씩 점유했습니다.
    조치
    핵심 기능인 예측을 지키기 위해 부가 기능을 중단했습니다. 예전 앱 요청에는 외부 호출 없이 빈 결과를 즉시 돌려줍니다.
    결과
    예전 앱에서 산책 조회 4건이 들어온 뒤에도 예측 작업이 큐에 바로 도달하는 것을 확인했습니다. 회귀 테스트 38개가 통과했습니다.

AI 판단을 어디까지 믿을 수 있을까

개인화 30%와 문헌통계 70%라는 비율은 실제 실종 사건 데이터로 정한 값이 아닙니다. 실제 실종자의 이동 경로 정답을 구할 수 없어서, 논문의 행동 특성을 조합한 합성 인물 39명의 시뮬레이션 경로로 비교해 고른 값입니다.

개인화 지도의 출발점도 사실이 아니라 추정입니다. 보호자가 들려준 생활사를 LLM(K-EXAONE)이 해석하고, SAR LoRA가 초기 이동 성향을 추정합니다. 이 해석이 틀릴 수 있다는 전제에서 설계했습니다.

실험 결과도 이 점을 보여줬습니다. 개인화 비중을 50·70·90%로 올리면, 예상과 반대 방향으로 움직인 사람의 포함률이 12.82~16.99%까지 떨어졌습니다. AI의 해석을 많이 믿을수록 예상 밖으로 움직이는 사람을 놓친다는 뜻입니다.

그래서 개인화는 30%로 두고, 개인 해석을 전혀 읽지 않는 문헌 통계 지도를 70%로 따로 계산해 결합했습니다. 그래도 반대 방향 이동의 포함률은 본선보다 2.88%p 낮습니다. 이 문제는 해결했다고 말하지 않고, 서비스도 공적 신고와 수색을 보조하는 도구로만 소개합니다.

다른 프로젝트에도 같은 원칙을 적용했습니다. 커리어 저금통은 근거가 부족하면 모델이 판단을 기권하고, dqa는 수정 성공 여부를 모델의 설명이 아니라 재측정으로 판정합니다. AI는 해석하고 제안하며, 검증할 수 있는 계산과 최종 판정은 코드와 사람이 맡습니다.

어떤 문제를 다뤘나요?

넓은 지역에 같은 알림을 보내면 알림 피로가 커집니다. 사전 등록한 정보로 수색 범위를 좁히고, 시민 제보를 다음 예측에 반영하는 흐름을 다뤘습니다.

어떤 일에 참여했나요?

생활사 해석을 위한 모델 비교, SAR·K-EXAONE·RAG의 연결 방식, 개인화·마음모델·보행 코드의 개선 방향을 논의했습니다. AI 코딩 도구와 함께 실험을 설계하고 수정·검증을 진행했습니다.

시스템은 어떻게 구성되나요?

  1. 클라이언트
    • Expo 앱 · 웹 (Cloudflare Pages)
    • 보호자 등록 · 실종 신고 · 시민 알림 · 제보
  2. 인증·작업 전달
    • Supabase Auth
    • 작업 큐 → 워커가 하나씩 처리
  3. CPU worker
    • 입력 검증 · 도로망 보행 계산
    • 개인화 지도 30% + 문헌통계 지도 70% 결합
    • H3 res9 알림 구역 선정 (최대 5.8㎢)
    • SQLite — 프로필·사건·제보·체크포인트
  4. 자체 GPU 모델 서버
    • EXAONE + SAR LoRA (vLLM 멀티 LoRA): 사건 정보 → 초기 이동 전략 비율·장소 끌림·반경 등급
    • Mi:dm 2.0 Mini: 시민 제보 문장 → 시간·장소 구조화
  5. 외부 API
    • KT Mi:dm: 보호자 대화 → 사실·장소 추출
    • Upstage embedding: 질문 → 관련 연구 문헌 검색 (RAG)
    • K-EXAONE: 보호자 원문 + 검색 근거 → 개인화 보정·조건별 행동 규칙

등록 때 보호자 대화를 해석해 행동 규칙을 준비합니다. 신고 때는 SAR 초기 수치와 연결해 보행을 계산하고, 두 지도를 결합해 알림 구역을 고릅니다. 제보는 구조화한 뒤 지도 갱신과 재예측에 씁니다. 모델은 해석과 추정만 맡고, 좌표·확률·구역은 코드가 계산합니다.

서비스는 어떻게 동작하나요?

  1. 생활사 사전 등록
  2. 동선 확률 예측
  3. 최소 구역 알림
  4. 시민 제보 반영

해석과 위치 계산의 역할 분리

LLM은 성향과 행동의 정성 해석을 맡고, 좌표와 확률지도는 통계·도로망 알고리즘으로 계산했습니다.

제보를 다음 예측에 연결

제보의 시공간 정보를 구조화하고 신뢰도에 따라 지도 갱신이나 새 기점 예측으로 연결했습니다.

실패가 사용자에게 보이도록

모델 실패 시 폴백을 구성하고, 예측 접수가 거절되면 반복 조회를 멈추고 안내하도록 개선했습니다.
