서비스 개요

문제 정의

실종 경보 문자는 어르신이 평소 어디에 갔는지에 대한 정보 없이 대상 지역 전체에 한 번 발송됩니다. 범위가 넓으면 시민이 알림을 지나치기 쉽고, 새 제보가 들어와도 수색 구역에 바로 반영하기 어렵습니다. 보호자가 아는 생활 정보와 시민이 목격한 정보를 모두 수색 범위 계산에 연결하고자 했습니다.

구현 방향

등록할 때 보호자 대화에서 사실과 조건부 행동 규칙을 뽑고, 원문에서 근거를 확인한 규칙만 저장합니다. 신고가 들어오면 SAR LoRA의 초기 이동 추정과 저장된 규칙으로 도로망 위 보행을 계산합니다. 규칙이 준비되지 않았을 때는 SAR 기본 추정으로 계산합니다. Expo 요청의 인증과 UUID 작업 큐, 작업 전달과 결과 저장은 Supabase가 맡고, 업무 데이터와 규칙, 접수증은 SQLite에 저장합니다.

내가 맡은 일

개발 팀장으로 AI 파이프라인 설계와 통합, 목적지와 행동 LoRA 학습 및 평가, vLLM 멀티 LoRA 서빙, 알림 정책 실험과 배포 후 운영을 담당했습니다.

Python, FastAPI, K-EXAONE, EXAONE 3.5, LoRA, vLLM, Mi:dm, Supabase, SQLite, H3, Expo

전체 아키텍처

등록할 때 보호자 설명을 해석

  1. 보호자 원문평소 습관과 장소, 보호자가 직접 관찰한 행동
  2. Mi:dm대화에서 사실과 원문 근거 추출
  3. K-EXAONE보호자 원문과 문헌에 근거해 조건, 행동, 인용문 생성
  4. Mi:dm 근거 확인생성한 조건과 행동을 보호자 원문과 대조
  5. SQLite확인한 규칙과 적용 상태 저장

신고가 들어오면 수색 구역을 계산

  1. 신고 정보실종 시각, 위치, 사건 조건
  2. SAR LoRAGPU의 vLLM에서 초기 이동 전략 비율과 이동 반경 등급 추정
  3. CPU 보행 계산수치를 검증하고 저장된 규칙을 도로망 위에서 실행
  4. 두 지도 결합개인화 보행 지도 30%, 독립 문헌 통계 지도 70%
  5. H3 구역코드가 좌표, 확률과 면적을 계산하고 Expo 지도에 표시

시민 제보를 접수하고 재예측

  1. 시민 제보Expo에서 목격 정보를 접수
  2. 접수증 저장SQLite에 기록하고 즉시 접수 결과 응답
  3. 백그라운드 작업Mi:dm Mini로 제보를 구조화하고 CPU에서 재계산

보호자 설명을 조건부 규칙으로 바꿔 보행 계산에 연결

내가 맡은 일 개인 해석과 SAR 초기 입력을 통합하고, 규칙 저장을 보행 코드에 연결했습니다.

관찰과 원인

보호자 설명을 성향 점수 6개로 바꾸면 “6분쯤 걸으면 쉰다” 같은 조건이 사라졌습니다. 기존 실행기는 6시간을 계산하는 동안 휴식을 한 번도 넣지 않았습니다. K-EXAONE에 해석과 수치를 함께 맡긴 출력은 70%에서 설명과 수치의 방향이 어긋났습니다. 해석만 맡겨도 약 31.8%에 보호자 원문에 없거나 원문과 반대인 내용이 들어갔습니다.

구현과 선택 이유

K-EXAONE은 보호자의 말에서 조건과 행동을 읽고, Mi:dm은 인용한 근거가 원문에 있는지 확인하도록 나눴습니다. 수치와 실행 시점은 코드가 계산합니다. 해석과 검증은 등록할 때 한 번 수행해 저장하고, 신고 뒤에는 개별 보행 계산이 모델 응답을 기다리지 않고 이 규칙을 재사용하도록 했습니다.

  1. 보행 시작0분에 걷기 시작
  2. 휴식6분에 앉아서 쉬기 시작
  3. 보행 재개5분 휴식 뒤 11분에 재개

수정 후 보존수정 사례 6개를 각각 2회 실행해 필수 항목 100/100과 초기 입력 연결 14/14를 확인했습니다.

평가 범위 합성 보호자 대본으로 등록, 저장, 보행 실행을 단계별로 확인했습니다. 이 검증은 실제 보호자 진술의 해석 정확도나 실제 실종 사례의 보행 예측까지 다루지는 않았습니다.

동네 이름만 바꿔 지명 편향을 찾고 목적지 LoRA를 재학습

내가 맡은 일 학습 데이터를 다시 구성하고 EXAONE 3.5 7.8B LoRA 학습과 평가, vLLM 어댑터 교체를 맡았습니다.

관찰과 원인

기존 dem3는 시연 동네인 정릉이 입력되면 75회 중 74회 목적지 후보를 냈지만, 형식은 두고 다른 10개 동네 이름으로 바꾸면 3회에 그쳤습니다. 정릉동 라벨이 있을 때 서로 다른 합성 프로필 5종은 각각 15회 모두 “끌림점 접근”만 골랐습니다. 기존 학습 정답 라벨은 “재래시장” 같은 일반명사로만 구성돼 있었습니다.

구현과 선택 이유

구체적인 지명도 답으로 낼 수 있도록 학습 예시를 추가했습니다. 지명이 정답 힌트가 되지 않도록 목적지와 평소 들르는 곳, 이름만 언급한 곳에 모두 실제 지명을 넣었습니다. 보호자가 해당 장소로 향하는 모습을 여러 번 본 사례는 후보를 고르고, 이동 근거가 부족한 사례는 보류하도록 구성했습니다. 생성기에서 평가 지명과 파생 표기가 학습 또는 검증 데이터에 들어가는지도 검사했습니다.

검증 결과

학습 데이터 누수 검사학습 1,332행과 검증 134행에 평가 지명 8종과 파생 표기가 들어간 경우는 0건이었습니다.

학습에 없던 지명으로 시험하고 만점이 나온 평가를 재검토

내가 맡은 일 봉인 시험을 실행하고 모델의 원응답을 다시 채점했으며, 평가기를 수정했습니다.

관찰과 원인

dem5 봉인 시험에서 혼란도와 행동 점수가 모두 100%였습니다. 혼란도 채점은 모델 원응답 대신 커밋되지 않은 운영 규칙이 바꾼 값을 읽고 있었습니다. 행동 시험에는 금지된 답이 하나도 없어 모든 상황에 “끌림점 접근”으로 답해도 모델과 같은 12/12를 받았습니다.

구현과 선택 이유

운영 규칙이 바꾸기 전의 응답을 채점하고, 항상 같은 답을 내는 기준도 동일한 방식으로 평가하도록 수정했습니다. 개발 시험에 저장된 같은 응답 32건을 다시 채점하니 모델은 24건(75%), 항상 “중”이라고 답하는 기준은 28건(88%)이 허용 범위에 들었습니다. 서비스의 혼란도 계산은 기존 규칙을 유지했습니다. 행동 지표는 이 시험으로 판단력을 구분할 수 없어 판정 불가로 정정했습니다.

검증 결과

확인 대상결과와 해석
목적지 적중학습에 없던 지명으로 나눈 12개 합성 상황을 4회씩 실행했습니다. 48회 중 40회(83%)에서 적중했고, 나머지 8회는 중립 응답이었습니다.
함정과 금지함정 상황 8/8을 회피했고, 금지 장소 선택은 0회였습니다.
행동 지표모델과 “항상 끌림점 접근” 기준이 모두 12/12였습니다. 행동 판단력은 판정 불가로 정정했습니다.

후속 행동 LoRA

데이터 72개와 보강한 120개, 학습 2, 4, 6 epoch를 비교했습니다. 같은 개발 입력 16개에서 행동과 근거가 함께 맞은 사례는 최대 10개여서 배포하지 않았습니다.

평가 범위 봉인 시험은 모델을 확정할 때 한 차례만 실행한 합성 시험 48회입니다. 실제 보호자나 실종자의 목적지 정확도는 이 시험으로 확인할 수 없습니다.

알림 면적을 제한하고 제보 접수를 재예측과 분리

내가 맡은 일 지도 결합과 정책 비교, 응답 처리 수정, 접수증 선저장과 백그라운드 복구를 맡았습니다.

관찰과 원인

개인화 비중을 50~90%로 높였을 때 예상과 반대로 이동한 경우의 포함률이 12.82~16.99%까지 떨어졌습니다. 배포 후에는 시민 제보 접수가 같은 사건 잠금과 계산 큐에서 대기했고, 응답도 백그라운드 재예측이 끝난 뒤 돌아오는 경우가 있었습니다.

구현과 선택 이유

개인화 보행 지도와 독립 문헌 통계 지도를 30:70으로 합치고, H3 셀 합집합의 실제 면적을 5.8㎢ 이내로 제한했습니다. 제보는 SQLite에 접수증부터 저장해 응답하고, 작업자 2개가 구조화와 재예측을 이후에 처리하도록 나눴습니다. 같은 submission_id로 다른 본문을 보내면 409로 거절합니다.

  1. 제보 요청시민이 Expo에서 제보 전송
  2. 접수증 먼저 저장submission_id를 검사한 뒤 접수 상태를 SQLite에 기록
  3. 접수 완료 응답저장 결과를 요청에 즉시 반환
  4. 분석과 재예측백그라운드에서 처리하고 대기 작업은 재시작 후 이어서 수행

접수와 분석을 따로 기록

1.63초는 합성 제보 한 건이 접수 완료까지 걸린 시간입니다. 이 검증에서 후속 지도 재계산은 실패했으며, 접수 완료와 분석 상태는 따로 저장했습니다.

평가 범위 알림 정책은 합성 인물 39명, 설정별 2,808판정으로 확인했습니다. 반대 방향 이동의 포함률은 30.45%에서 27.56%로 낮아졌고, 실제 사건에서의 성능은 검증 범위에 포함되지 않았습니다.
